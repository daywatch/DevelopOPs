10. terraform state

when you terraform apply again, there is no more update. This is because a state file is generated, called: terraform.tfstate
tfstate can be refreshed and synced like cache

unless you stop refreshing like: terraform plan --refresh=false

also, after apply, you can use terraform show to check ids

14. mutable and immutable infra

Mutable >>> in-place update means the underplying infra is the same, but the software change one by one as part of update

config drift >>> different instances/servers have different settings or environ, causing updating problems

Immutable >>> add a new server and remove out-dated ones; easy for versioning, going backward and forward


15. lifecycle rules

(1) create_before_destroy

resource "local_file" "pet"{
	filename = "/root/pets.txt"
	content = "we love ${random_pet.my-pet.id}"
	file_permission = "0700"
	
	lifecycle {
		create_before_destroy = true
	}
}

(2) prevent_destroy

Destroy prevention when there are changes made to config and a subsequent apply, not terraform destroy

(3) ignore_changes
Config will never change.

resource "local_file" "pet"{
	filename = "/root/pets.txt"
	content = "we love ${random_pet.my-pet.id}"
	file_permission = "0700"
	
	lifecycle {
		ignore_changes = [tags,ims] #or just ignore_changes = all
	}
}

37.workspace
use the same project directory for multiple environments like projects

terraform workspace new ProjectA
terraform workspace list
terraform workspace select ProjectB

Suppose we want to create two projects with different AMI ids but other settings are the same. In variable.tf:

variable region{
	default = "ca-central-1"
}
variable instance_type {
	default = "t2.micro"
}
variable ami{
	type = map
	default = {
	"ProjectA" = "ami-123",
	"ProjectB" = "ami-789"
	}
}

in main.tf:
resource "aws_instance" "ProjectA"{
	ami = lookup(var.ami,terraform.workspace)
	instance_type = var.instance_type
	tags = {
		Name = terraform.workspace
	}
}
